Date: 2026-09-26. Protocol revision: 3.

## 1. Question and exact groups

Does handing an ongoing task to a reconstructed context preserve its effective
goal, constraints and progress better than another native Pi compaction? Does
our plugin retain the benefit of the original Handoff skill?

Every work cycle grows active input to approximately 250,000 tokens. Use the
same task fixtures, user-message schedule, starting workspace and independent
repetition seed in every group. The history before each transition follows the
group's schedule below; D deliberately has no native-compaction history.

| Group | Boundaries 1–3 | Boundary 4 | Continuation |
| --- | --- | --- | --- |
| A: native Pi | Native, native, native | Fourth native Pi compaction | Existing session, native summary and native retained tail |
| B: original Handoff | Native, native, native | Invoke the pinned original Matt Pocock skill to write a handoff document | Fresh Pi session, original handoff document and referenced artifacts |
| C: Context-handoff | Native, native, native | Load the plugin at native limit 3 | Same visible conversation, installed Task State and Pi-retained tail |
| D: zero-native Context-handoff | Plugin Handoff at every boundary; zero native compactions | Fourth direct plugin Handoff | Same visible conversation; no native summary in the tested history |

Expected schedules: **A `NNNN`; B `NNNB`; C `NNNC`; D `HHHH`**, where `N` is a
native Pi summary compaction and `H` is a committed Context-handoff transition.
`B` means skill-document generation followed by a fresh successor; it is not a fourth
native compaction. D answers whether our plugin can carry the task when native
summary compaction has never been used. The main comparison ends after boundary
4 and the common final task. Later boundaries are a separate protocol.

A is actual native Pi without Context-handoff's tools or hooks. B also runs
without that plugin. C and D use the same frozen plugin build with different
native-success limits. Consequently, this is a comparison of complete workflows;
effects cannot be attributed exclusively to the handoff document, the source
summary format, or context reset in isolation.

## 4. Construct four genuinely large work cycles

### Size definition

The target is **250,000 active input tokens**, with an admission band of
245,000–255,000, immediately before each of the four maintenance boundaries.
Include system instructions, tool schemas, active messages and existing summary.
Do not substitute characters, UTF-8 bytes, files on disk, cumulative billable
input, or the sum of inputs from multiple requests.

Use provider-reported input usage to calibrate the actual serialized request,
including cached input exactly once according to that provider's usage format.
Record the final pre-boundary request and the subsequent small completion/tool
delta. Independently record Pi's estimate and any tokenizer estimate; an
unverified estimate cannot certify a 250k case. If the exact maintenance
projection cannot be counted, retain the observed request count and explicitly
bounded delta; reject the 250k label if that bound crosses the admission band.

Measure the native summarizer, B's document generator and C/D's plugin
synthesizer separately. Native Pi can split summarization into two requests, and
the plugin deliberately selects a smaller source input. These transition
requests need not each contain 250k tokens. The common pre-transition **working
context** must meet the target.

### Workload construction

1. Start with a synthetic but coherent repository task and the case's original
   requirements. Add versioned specifications, code-review work, varied logs,
   test results, decisions and corrections through normal Pi user/tool turns.
2. Grow to the target, settle all tools and capture boundary 1. After the
   assigned transition, add new work to refill the active context before
   boundaries 2 and 3, then refill again before boundary 4. This applies to D's
   repeated Handoffs as well as the native transitions in A/B/C; only the
   transition type follows each arm's schedule.
3. Use unique, task-related material; do not fill the window by repeating one
   sentence or replaying the same giant log. No fake successful tool messages
   or text appended only in the provider proxy. Large files count only to the
   extent their contents actually reach model requests; Pi read truncation
   must be observed.
4. Freeze payload seeds, chronology and fact locations before results. Spread
   critical facts across early/middle/late history and work cycles. Most older
   standing constraints must precede the native retained tail. Include recent
   facts as controls and report their positions; do not move facts after seeing
   which arm misses them.
5. Every turn of D01–D13 must remain represented in every group. Default mapping: original
   turns 1–2 in cycle 1, 3–4 in cycle 2, 5–6 in cycle 3, and turn 7 in cycle 4;
   insert new work after these turns to reach the target. Apply fixture changes
   at their original relative turns. Send the final task only after boundary 4.
6. Adapted cases get new versioned fixture IDs and hashes. They are derived
   long-context cases, not reruns of the unchanged seven-boundary bank.

## 5. Shared prefix and checkpoint fairness

For each case and repetition, create one immutable starting project and a
predeclared chronological stream of user requests, files and environment changes.
Make isolated copies for each arm. Keep the user prompts and exogenous project
changes identical; model responses, tool actions, active-context contents and
session entries are treatment outcomes and must not be forced identical.

Run A/B/C/D with separate histories and isolated workspaces. A/B lack the plugin's
extra tools and hooks, while C/D have them; sharing a three-native prefix would
therefore change their available request schemas and fail the specified treatment
conditions. D starts from the same pre-boundary-1 state and receives the same work
cycles without native compactions; it performs Handoff after each one. D cannot
be restored from a three-native checkpoint, because that would violate its
zero-native definition. Check and hash each arm's branch lineage, workspace,
current project state, tool settings and visible input at every intervention. Log
treatment-specific schemas and handoff instructions.

At the first 250k boundary, A and D also provide a matched transition comparison
from the same starting scenario: A performs native compaction and D immediately
performs the plugin Handoff. Preserve that first-boundary pair when reporting
the overall four-boundary results.

Each scenario/repetition is one **matched quadruple** of A/B/C/D. The A/B/C
shared prefix does not make separate repetitions independent. Build a fresh
prefix for every repetition. Balance transition order where prefixes are
independently generated; avoid simultaneous calls if they could cause route
throttling, and record timing/provider incidents.

Record original setup checkpoints (for example, D07's first three ledger lines
and D11's first fixture) at the corresponding user turns. Structural setup
failure affects the entire quadruple and is reported before treatment. Do not
discard a valid prefix merely because a separate pre-transition probe reveals
semantic drift: recovery from that drift is part of what B/C should be tested on.

## 6. Execute each fourth transition faithfully

### A — native Pi at all four boundaries

Use Pi's public compaction operation without custom summarization instructions,
Context-handoff extension or recovery tools. Capture the committed native entry,
summary, retained IDs and the first subsequent model request at each boundary.
Require schedule `NNNN` and no Handoff entry.

### B — original skill and fresh successor

1. At boundary 4, explicitly invoke the pinned skill, with the neutral focus
   `Continue the existing authorized task.` This administrative instruction is
   the skill invocation, not a new task permission or a restatement of answers.
2. Use the unchanged original skill through Pi's supported skill mechanism.
   The outgoing agent starts with the current P4 conversation, including the
   three native summaries' current projection; do not secretly supply a full
   uncompressed transcript. It may read ordinary accessible artifacts.
3. Let it create the handoff document in an isolated OS temporary directory.
   Preserve its exact contents, references, tool trace, token usage and hash.
   No human corrections, hidden answer hints, rewriting, best-of-N generation,
   added structured-state checks or an additional compaction are permitted.
4. Launch a **fresh** Pi session with the same workspace, baseline instructions,
   model/settings and B's pinned original skill. Keep referenced legitimate
   artifacts available. The temporary document must remain readable across the
   launch. Preserve outgoing and successor session entries separately, and label
   both segments in the combined scoring input so B's first three native
   summaries are not omitted.
5. The successor receives only baseline instructions, a pointer to the generated
   document, and the exact common final task: `Read the handoff document at
   <path>, then address this user request: <final task>`. Do not preload old
   conversation messages, a second researcher-written summary, or source answers.
   Log whether it reads the document and follows relevant references.
6. Missing/empty handoff documents, broken references, unreadable temporary
   files and failed skill loading are reported separately from task mistakes.
   Record whether the successor actually reads the generated document. A new
   physical session is expected for B and is not a continuity failure.

B is the **unmodified skill hosted in Pi plus a mechanical fresh-session
transfer**. The skill's document generation and the harness's session transfer
must be separately visible in evidence. Do not claim an unchanged upstream
runtime: the upstream artifact is a prompt/skill, not a supplied Pi runner.

### C — plugin after three native compactions

Load only the frozen Context-handoff extension on restored P4. Invoke the same
public compaction boundary. Require the plugin to observe count 3, prepare its
state and commit its entry. Capture source selection, excerpt coverage, limits,
repair attempts, actual retained messages and the outgoing request.

Do not add B's fresh-session step, original skill prompt, human review or a new
successor checklist to C. Those would create a different candidate. C is allowed
its own recovery/guard mechanisms and its specified fallback behavior.

### D — plugin from zero native compactions

Run the same frozen plugin build as C with `--handoff-native-limit 0`. Trigger it
at every one of the four measured boundaries; require `HHHH` and zero native
compaction entries. At the first boundary D makes a direct Handoff from the
same initial pre-transition state used by A, before either group has compacted.
At later boundaries D has previous plugin Handoffs in its history, which is
part of the zero-native workflow under evaluation.

This limit is currently rejected by the configuration validator. Before the
pilot, extend the accepted range to start at zero (or expose an equivalent
supported public trigger), keep the normal default at three, and test through
Pi's public interface that limit 0 hands off at the first boundary and resets
the native count correctly after each Handoff. Run C against that exact same
build at limit 3. Pin the zero-limit change and classify the result as a new
plugin candidate. The existing build cannot execute D as specified.

If preparation falls back to native, label the transition `C-fallback-to-N` or
`D-fallback-to-N`, according to the assigned arm. Keep its task outcome and cost
under that arm, and record the actual schedule. A fallback in D violates its
zero-native treatment; retain the attempt in the assigned-D operational results,
but do not count it as a successful `HHHH` run or as evidence about zero-native
Handoff fidelity. Do not relabel it A or silently retry until a Handoff succeeds.

### Common continuation and scope

For this main comparison, maintenance is manually initiated at the measured
target, automatic compaction is disabled, and each arm receives the same final
task wording after boundary 4. D receives the same scheduled maintenance
operation at every boundary, with the plugin handling each one. B's document
pointer is its required bootstrap wrapper. C/D receive no extra reminder or a
repeated numeric answer. Freeze this wording. The target remains a real 250k Pi
conversation, not a proxy-only model prompt.

Because C suppresses automatic continuation after manual compaction, this lane
measures **prompted task continuation fidelity**, not autonomous resumption.
Record any unexpected transition-side actions, especially cancelled work, but
do not penalize A or the original B skill for requiring this final user request.

Seamless automatic continuation remains a separate C product-acceptance lane:
trigger an actual Pi automatic boundary, observe the hidden continuation and
subsequent requests without a user “continue,” and check stopped/done work stays
stopped. That lane requires its own frozen trigger/headroom configuration and
is reported separately. Changing Pi's reserve also changes native summary output
budgets; do not change it invisibly to force 250k triggering. The main ABC result
must not be advertised as proof of this separate capability.

## 9. Execution stages and bounded budgets

1. **Local readiness:** implement the new runner, fixture version, skill transfer,
   wire capture and scorer. Verify schedule/restore/transfer behavior through Pi's
   public interface. Existing `evaluate-drift.mjs` is not this protocol: it has
   seven small manual boundaries, a 131,072 window and zero recent retention.
2. **Route and sizing calibration:** confirm a real approximately 250k request
   through the chosen route and calibrate usage accounting. These calls are
   preflight evidence, not scored task trials. Record missing usage or upstream
   input truncation; do not assume HTTP 200 proves the requested input was used.
3. **Pilot:** D01, D05, D07 and D10, one independent matched quadruple each:
   **four matched quadruples / 16 arm attempts**. Confirm four large cycles, B's
   actual fresh bootstrap, C's trigger at boundary 4, and D's zero-native direct
   trigger plus a Handoff at every boundary. Any D native fallback invalidates
   that attempt's `HHHH` treatment-faithful status, but remains in the assigned-D
   operational report.
4. **Formal cohort:** after freezing any pilot-driven revisions, use new seeds
   and independent histories for D01–D13, three repetitions:
   **39 matched quadruples / 156 arm attempts**. Run all four arms from the
   starting state with independent histories; A/B/C each perform their scheduled
   three native boundaries and D performs zero native boundaries. Pilot results
   remain separate. Three repetitions support descriptive comparisons;
   they are not enough to declare universal or model-independent superiority.

Initial external caps: 300 seconds per provider request, 600 seconds per
maintenance transition, 32 provider requests per transition, 900 seconds and 64
requests per post-transition task. Set common agent output ceiling to 32,768
tokens and reasoning to medium. Native summary ceilings remain those computed by
pinned Pi from its frozen reserve; C/D synthesis remains 16,384 tokens with its frozen
120,000 ms internal deadline and one bounded field repair. Report these internal
differences; the external envelope is a stop limit, not a claim of identical
internal computation. Any tuning after calibration must create a new frozen
manifest before the pilot or formal run it affects.

Each prefix work cycle has a 1,800-second/128-request cap; stop a prefix after
7,200 seconds or any cycle cap. Size the workload locally before paid runs.
Disable automatic provider retries. Preserve interrupted attempts; any retry
has a new attempt ID and is never selected because its answer is better.

Do not expand to the formal cohort if 250k accounting, B portability, matched
starting-state fidelity, D's zero-limit trigger or input capture is broken. If
either plugin arm cannot commit a Handoff in the pilot because of a deterministic
limit, report that operational result first; repeating the same blockage across
156 attempts would not answer Handoff fidelity. Fixing it creates a newly named
C/D plugin candidate and cohort, rather than erasing the failed pilot.

- `scores.json` and `report.md`: frozen scorer version, objective verdicts,
  phase/cause attribution, all-attempt and complete-quadruple views, paired results,
  costs, limitations, and the first stage at which each error is evidenced.

The runner entry points are `scripts/lint-abcd-fixture.mjs`,
`scripts/run-abcd.mjs` and `scripts/resume-abcd.mjs`. The first serializes all 16
pilot attempts and stops on provider quota/rate-limit responses. It can import

repeated. The resume driver preserves every earlier artifact and assigns a new
attempt ID and output directory to each follow-up attempt; `--dry-run` validates
the plan without contacting the provider. B's generated document, outgoing

## 11. How results change the decision

| Observation | Supported conclusion |
| --- | --- |
| B repeatedly succeeds where A fails | The original Handoff workflow helps on this workload/model. |
| B helps, C does not | Inspect differences in transfer content, source selection, retained context, bootstrap and extra guards. It is not evidence against original Handoff. |
| C matches or exceeds B with reliable transitions | The plugin preserves or improves the measured baseline; automatic user-transparent continuation still needs its separate acceptance lane. |
| C mostly falls back | Current plugin preparation/scale reliability prevents a useful fidelity estimate. |
| D matches or exceeds C with reliable `HHHH` runs | Direct repeated plugin Handoff is viable on this workload without native-summary history; this does not prove universal fidelity or isolate a single mechanism. |
| C succeeds more often than D | The three-native-prefix workflow is more reliable here; inspect source selection, repeated Handoff history and fallback causes before attributing the gap. |
| D mostly falls back to native | The zero-native workflow is not operationally reliable on this setup; its assigned-D outcomes remain reportable, but there is little treatment-faithful evidence about zero-native fidelity. |
| A/B/C/D all succeed | The bank has not demonstrated a comparative advantage; report a ceiling effect without manufacturing harder cases after seeing outcomes. |
| A/B/C/D all fail | Inspect task validity, pre-existing drift, source accessibility and model execution before blaming the transition. |

This round compares **four named workflows at the same
large-context boundary**. C vs D is a comparison of complete schedules (three
native prefixes plus plugin Handoff vs repeated plugin Handoffs), not an isolated
causal estimate of native summaries alone. It does not determine an optimal
compaction count, prove zero drift, or justify abandoning the original Handoff
principle from a failure of the custom implementation.
