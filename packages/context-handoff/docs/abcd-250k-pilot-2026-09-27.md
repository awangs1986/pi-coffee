# ABCD 250k pilot — completed diagnostic report

Date: 2026-09-27. Protocol: [`测试方法.md`](../测试方法.md), revision 3.

## Status

The pilot has terminal records for all 16 predeclared case/arm combinations
(D01, D05, D07 and D10 × A/B/C/D). Retries are retained as separate attempts:
the cohort manifest contains 20 attempt records, 19 scored runs and one
interrupted partial run. The final resume completed all six of its planned
attempts. `COMPLETE` describes runner completion; it does not mean the
treatments were valid or comparable.

Provider/model/thinking: CommandCode `meta/muse-spark-1.3-contributor`,
**medium**. Declared context window: 524,288 tokens. Required active-prompt
admission band: 245,000–255,000 tokens at each of four boundaries. The A
control passed all four boundaries on D01/D05/D07. D10 was outside the band
after boundary 1 for every arm, so those attempts are invalid for comparison.

Across the 19 scored attempts, the recorder captured 1,286 provider requests,
151,077,769 prompt tokens and 474,236 completion tokens. These are cumulative
request totals across repeated history and retries, not the active context size
at a boundary. The first pass stopped at the provider's five-hour limit; the
resumed pass completed without another 402/429 response.

### B — original Handoff skill

The initial D01/B and D05/B attempts did not transfer the generated document;
D07/B then hit the provider's five-hour limit after two boundaries. Those
attempts are invalid for semantic comparison.

The three corrected retries reached the intended schedule `NNNB` and stayed in
the admission band, but the successor still did not receive the document. In
all three retries `handoffDocument.candidateCount` was 0,
`handoffReadObserved` was false, and the successor read
`/tmp/handoff/MISSING-HANDOFF.md`. The original skill's successful `write` tool
outputs appear in the recorded Pi events, while the runner's staged OS-temp
directory remained empty. Thus the mount change did not repair transfer
through the tool boundary.

D01/B also failed the exact UTC-Z timestamp requirement (`+08:00` was written).
D05/B and D07/B produced the expected final content/checkpoint, but they still
fail the B treatment because the successor never read a handoff document.

### C and D — Context-handoff schedules

All scored C runs for D01/D05/D07 completed the task, but actually used native
compaction at boundary 4: `NNNN`, rather than `NNNC`. The partially interrupted
D07/C attempt 1 reached only `NNN`; its files are retained and it is not scored
as a completed run. Attempt 2 completed and is the D07/C row above.

All D tasks for D01/D05/D07 completed, but each used at least one native
fallback: `NHNN`, `NNHH` and `NHHH`. None is evidence for the declared `HHHH`
zero-native treatment. These schedule failures are product reliability
findings, not fidelity wins.

### D10 — context-size admission failure

The D10 first boundary was in range for all four arms (247,731–247,864 tokens).
At boundary 2, all four fell below the 245,000-token lower bound by about 2.5k
tokens (242,375–242,526). The evaluator stopped each prefix as designed. These
attempts cannot answer D10's fidelity question; the D10 workload must be
recalibrated and versioned before rerunning all four arms.

## Interpretation

This pilot **does not establish whether B, C or D preserves context better than
four native compressions**. A is a valid 3/3 control on D01/D05/D07. B has no
valid successor-document transfer. C and D did not follow their declared
treatments. D10 failed the context-size admission check in every arm. Reporting
any A/B/C/D winner from these data would overstate the evidence.

The useful product finding is narrower: the current plugin candidate often
completed these tasks even when its requested transition fell back to native
compaction, but it did not reliably commit the tested C/D schedules. The pilot
also found two harness issues that need correction before the groups are
comparable: B document staging and D10 context calibration.

## Required follow-up before a comparative cohort

1. Fix B transfer at the tool boundary. Stage only a successfully completed
   `.md` `write` tool result into the successor's shared handoff directory, or
   make the OS-temp mount visible to the tool executor. Require a nonempty
   document hash and an observed successor `read` before accepting a B run.
2. Recalibrate D10's cycle-2 load, assign it a new fixture version, and verify
   all four arm prefixes are 245k–255k at every boundary before scoring them.
3. Fix the plugin's preparation/fallback behavior, then rerun C and D against a
   frozen candidate so C reaches `NNNC` and D reaches `HHHH` without fallback.
4. Start formal repetitions only after the above pilot checks pass. Keep the
   existing attempts immutable and use new attempt/cohort identifiers.
