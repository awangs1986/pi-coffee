# PI Coffee 0.1 release contract

0.1 turns the MVP conversation seam into the internal multi-user deployment discussed in the design session. It is a product contract for the next tickets; an item is not complete until its acceptance evidence is posted to Gitea.

## Release outcome

An internal user authenticates with Gitea in one Browser Shell, selects one of their fixed User VM sessions, and can run multiple Tasks/Pi Sessions from the Web VM. Pi keeps working when the browser disconnects. User content remains in the User VM; the Control Plane routes and relays but does not become a transcript store.

## Required slices

### 1. Control Plane and central LLM Relay

- Relay the CPA Chat Completions and Responses endpoints with JSON and SSE pass-through.
- Store the sole upstream credential on the Control Plane.
- Strip client credentials and add the central credential at the Relay seam.
- Preserve `/v1/models` and `/v1/responses/compact`.
- Bound request/response metadata and never persist prompt bodies.

Acceptance: a Host with no upstream key can complete a text and image-capable model request through a local Relay stub and the stream is not buffered.

### 2. Gitea identity and User VM routing

- Complete Gitea OAuth against the internal Gitea instance.
- Bind each internal user to one fixed User VM/Agent Host identity.
- Issue/revoke transport enrollment credentials without exposing the LLM key.
- Fail closed when a route or Host identity is missing.

Acceptance: two test identities cannot attach to one another's Session, and a Host restart does not silently change the assigned VM.

### 3. Agent Host deployment

- Provide the idempotent Deployment Skill and systemd unit for Linux Mint Xfce User VMs.
- Install the pinned original Pi package plus PI Coffee Host.
- Enroll with a one-time token and emit a human-readable report.
- Support health, graceful stop, and manual VM snapshot restore.

Acceptance: a clean User VM can be enrolled twice without duplicate processes or lost native sessions.

### 4. Browser Shell, Tasks, and Sessions

- Keep one browser tab while exposing multiple Tasks and Pi Sessions.
- Persist session/task identifiers and cursors in the User VM; keep only opaque routing state on the Control Plane.
- Reconnect after refresh or browser close and continue an active run.
- Serialize writes to one Task worktree; independent Tasks may run in parallel.

Acceptance: close the tab during a long fake run, reopen it, and observe completion plus replay exactly once in the Browser Shell.

### 5. Uploads and images

- Stream files to the Task inbox in the User VM.
- Enforce the 256 MiB/file and 1 GiB/batch limits, safe names, MIME checks, and SHA-256.
- Preserve original image bytes and select image block vs path/reference according to model capability.
- Make download/reference links scoped to the owning user and Task.

Acceptance: a text file and image survive browser reconnect; the Control Plane has no durable body or thumbnail.

### 6. Failure and recovery evidence

- Document Web Server, Relay, Host, Gitea, and VM failure states.
- Keep active Host Sessions running through browser/transport loss.
- Make manual VM snapshot restore the documented recovery operation.
- Record health and usage metadata without copying context正文.

Acceptance: each failure probe has a deterministic user-visible state and a recovery command in the runbook.

## Deliberate 0.1 non-goals

- No Picode VM manager.
- No in-VM command sandbox or permission approval layer.
- No V5 code migration, Worktree redesign, or plugin split in this release contract.
- No public internet exposure for Gitea.
